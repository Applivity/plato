1. Add a change-log row (date, commit hash or "this commit", area,
   summary, how verified) for every meaningful change, before you push.

   verified, with evidence (command output, screenshot, transcript).

## Deferred / backlog (do not lose these)

- **How to bound `auto` now that no turn cap exists (opened 2026-09-24, deliberately not
  solved).** D49ab removed `MAX_TURNS` from every mode. In `plan`/`edit`/`act` that is
  plainly right — an approval card gates every write, so the user IS the backstop. In
  `auto` there is no click in the loop, so **nothing stops a model that keeps calling
  tools without concluding.** The founder's own view, recorded because it is the reason
  this is a backlog item and not a repair: *models conclude their tasks anyway*, and the
  runway fear may be exaggerated — Claude Code ships an auto mode with no turn limit.
  **What a bound should NOT be, learned the expensive way:** a step count. D49ab removed
  one that had been applied to every mode and cut a *working* run at two-thirds after the
  user had approved eleven writes; and turns measure the wrong thing — that run spent
  10,442 output tokens across 40 turns, while a thinking run can spend more in three. **A
  user-set `$/turns` budget was built once and removed the same day as an unrequested
  capability (D49h) — do not re-propose it as the answer without reading that entry.**
  **The promising shape, not yet designed:** the failure mode is **repetition**, not
  volume — a model re-issuing the same tool call with the same arguments after it failed.
  Detecting a repeated identical call and stopping with a report bounds the actual fault
  instead of guessing a number. **Also worth considering:** `duo`/`academy` already put a
  supervising observer in the loop, which is the structural answer for an unattended run —
  an `auto` run under an observer is supervised where a solo one is not.
- **Ordering the model list, so the user controls picker priority (founder-requested
  2026-09-23, deliberately held back).** D49z deleted the tick boxes, so a connection's
  model list is now the fetched list in stored order, and the chat picker shows that
  order. The founder wants to control it: **drag to reorder**, or up/down arrows, with the
  order shown in the picker. **Why it is worth more than cosmetics:** when the chosen
  model stops being offered, `pickEffectiveModel` falls back to the first available model
  — so the top of the user's list becomes their stated default, which answers a question
  that already exists. **Four things to settle before building it:** (a) drag-only
  reordering has **no keyboard path**, which is wrong for a keyboard-first product, so
  ship arrows or row buttons with it; (b) HTML5 drag-and-drop is **hard to drive from the
  render harness**, so the order logic (*move i to j*, and *merge a refreshed list into
  the user's order*) belongs in core as tested pure functions, leaving a thin
  manually-verified gesture; (c) it is a **capability, not a repair** — do not fold it
  into a fix; (d) it does not scale — dragging is for five to fifteen models, and on a
  provider returning hundreds the search box is the real answer. **Merge rule when it
  lands:** keep the user's order for models still offered, append new ones at the END
  (never insert by rank), and do not remember the position of a model that disappeared.
- **Plato never reads a reasoning model's thinking tokens (found by the second real
  run, 2026-09-22).** The OpenAI-compatible adapter reads `delta.content` and nothing
  else, so `reasoning_content` — the field DeepSeek-R1-class models put their thinking
  in — is **discarded entirely**. Three consequences, in increasing order of importance:
  the model's reasoning is invisible to the user; those tokens are billed as output but
  never shown; and a turn that spends its whole budget on reasoning arrives as an
  **empty** turn, which is the condition that triggered D49s. **Not fixed, and not
  obviously a bug to fix** — streaming someone's raw chain-of-thought into the panel is
  a product decision (Claude Code shows a collapsed thinking block; some tools show
  nothing), and reading the field does not by itself decide what to do with it. What is
  clearly wrong today is that the tokens are counted and then thrown away with no note.
  **Do not build a thinking display without the founder.**
- **The context-window fallback only helps when the connection reports one (D49t,
  2026-09-22).** Steps 1–3 of the founder's plan are built: the discovered numbers now
  reach the RUN (not just the header), discovery happens automatically before a run, and
  the missing fields are read — vLLM's `max_model_len`, and LiteLLM's `/model/info`,
  which is the only place LiteLLM publishes sizes. **What still reaches the 8,192 floor:**
  a provider that reports nothing (plain OpenAI's own `/models` carries no window at all),
  an endpoint that refuses `/model/info`, and any connection where discovery simply fails.
  **Two unbuilt options remain the founder's call:** (4) a per-connection window the user
  declares, which is the only input that is correct by construction rather than discovered
  — and would want a settings screen; (5) **Ollama and llama.cpp**, whose windows are
  runtime values on different endpoints (`num_ctx` in `/api/show`'s parameters, or the
  served value in `/api/ps`; `n_ctx` in `/props`). **Ollama is the cautionary case:** it
  advertises its TRAINING maximum — often 128k — while serving a fraction of it, so its
  reported number must never be taken at face value. Nothing here needs building until
  Plato is pointed at a setup discovery cannot read.

- **A model outside the catalog is assumed to hold only 8,192 tokens (found by the
  first real run, 2026-09-22).** `maxContextFor` returns `null` for a model name it
  does not know, and `shouldAutoCompact` then uses `UNKNOWN_CONTEXT_FLOOR` = **8,192**,
  so compaction trips at ~6,553 tokens. **Any LiteLLM group name or custom/self-hosted
  model hits this** — the run that found it used a LiteLLM group called `Auto-Act`,
  and three Java files plus a few tool results were enough. The consequences are that
  conversation history is summarised far earlier than it needs to be, and (until the
  compaction-split fix in the same commit) that each compaction produced an **invalid
  request** rather than a shorter one. **The fallback is deliberate** — the loop records
  that trusting a `/models` payload for the window was rejected because OpenRouter and
  LiteLLM routes report stale or route-specific windows — so the fix is not simply to
  trust the endpoint. **Options, not yet chosen:** a per-connection context-window field
  in `plato.connections` (explicit, user-owned, no guessing); a larger floor (safer but
  arbitrary); or reading the window from `/models` only when the user opts in. **Do not
  pick one without the founder** — this is a product decision about where the number
  comes from, and the wrong answer either compacts too eagerly or overflows the window.

  this is the note so it is a decision rather than an oversight.
